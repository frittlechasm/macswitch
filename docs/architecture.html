App Switcher Architecture

Human-readable architecture report for the native Swift/AppKit macOS app switcher prototype. The agent-readable companion is docs/architecture.md. Prepared for engineering review on 2026-06-09.

The system is a SwiftPM macOS executable that runs as a menu-bar accessory app, registers an Option-Tab shortcut, builds a current-workspace window candidate list from public macOS APIs, renders an AppKit overlay, and activates the selected window through Accessibility with an app-level fallback.

Executive Summary

Source-backed App Switcher is a small native macOS prototype with explicit service boundaries for permissions, hotkey input, window inventory, workspace filtering, overlay rendering, and activation. Gap The app has no automated tests, no signed app bundle, no configurable hotkey UI, and only a public-API approximation of Space membership.

System Purpose

Source-backed The README describes a native Swift/AppKit macOS app switcher prototype that uses public macOS APIs, Accessibility for discovery and activation, app icons plus window titles, visible non-minimized workspace filtering, and an Option-Tab shortcut (README.md:1-11).

Source-backed The domain glossary defines an App Switcher as a keyboard-driven macOS overlay for moving focus between visible work items, and a Workspace as the active macOS Space/Desktop (CONTEXT.md:5-11).

Data Model and Storage

Source-backed The only domain data structure is WindowCandidate, which stores process id, app name, bundle id, title, frame, app icon, and the Accessibility window reference (WindowCandidate.swift:4-12). Source-backed There is no persistent storage, database, cache, or migration layer in the current file inventory.

External Integrations

Source-backed The app integrates with macOS frameworks only: AppKit for app lifecycle, menu, overlay, and screens; Carbon for hotkey registration; ApplicationServices Accessibility for permission/window control; and Core Graphics for visible window-server state.

  • AXIsProcessTrusted and AXIsProcessTrustedWithOptions check/request Accessibility trust (AccessibilityPermissionService.swift:6-15).
  • RegisterEventHotKey registers Option-Tab (GlobalHotKeyMonitor.swift:48-56).
  • AXUIElementCopyAttributeValue reads window attributes (WindowInventoryService.swift:85-95).
  • CGWindowListCopyWindowInfo reads on-screen window-server snapshots (PublicWorkspaceFilter.swift:25-29).

Architecture Decisions

Native Swift/AppKit executable

Source-backed The project is a SwiftPM executable targeting macOS 13, with AppKit lifecycle code at runtime (Package.swift:5-18, main.swift:3-8). Tradeoff: fast native integration with macOS APIs, but no Xcode app-bundle packaging yet.

Public-API workspace approximation

Source-backed Filtering is implemented through on-screen Core Graphics windows and screen intersection rather than private Space APIs (PublicWorkspaceFilter.swift:25-88). Tradeoff: distribution-friendly and less brittle, but exact Space membership may be imperfect.

Service-per-responsibility composition

Source-backed AppDelegate directly constructs permission, inventory, filter, activation, overlay, session, menu, and hotkey services (AppDelegate.swift:11-37). Tradeoff: simple for a prototype, but dependency injection is manual and not yet test-oriented.

Security Controls

Source-backed The app explicitly checks Accessibility trust before listing windows (SwitcherSessionController.swift:39-44) and exposes a settings path for permission management (AccessibilityPermissionService.swift:18-26). Source-backed It does not use network APIs, store secrets, or write user data in the current codebase.

Gap There is no signed/notarized app bundle, entitlement review, hardened runtime configuration, or release packaging yet. That matters because the product goal includes eventual public distribution.

Gaps and Risks

Space membership is approximate

Gap The code uses visible window snapshots, titles, PID, and frame overlap as a proxy for current workspace membership (PublicWorkspaceFilter.swift:61-88). Severity: medium, because edge cases across Spaces, fullscreen apps, Stage Manager, and multiple displays need manual validation.

No automated tests

Gap The SwiftPM package defines only an executable target and no test target (Package.swift:10-18). Severity: medium, because filtering and session transitions are behavior-heavy and easy to regress.

Hotkey is hard-coded

Gap Option-Tab is registered directly in GlobalHotKeyMonitor (GlobalHotKeyMonitor.swift:48-56). Severity: low for prototype, medium for public release.

Overlay shows only seven candidates

Source-backed The overlay frame and drawing logic cap visible items at seven (SwitcherOverlayController.swift:50-51, SwitcherOverlayController.swift:91-93). Gap There is no overflow affordance yet.

Recommendations

  1. Add a test target for candidate filtering, session state transitions, and activation fallback boundaries.
  2. Introduce a configurable hotkey model before exploring Command-Tab replacement.
  3. Build an app-bundle packaging path with signing/notarization before public distribution.
  4. Record manual test results for Spaces, fullscreen apps, Stage Manager, multi-display setups, Chrome, Terminal, and Finder.
  5. Add overlay overflow handling for more than seven candidates.
